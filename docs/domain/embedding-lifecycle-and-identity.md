# Embedding Lifecycle and Identity

Sprint 1-E2. See ADR 0016 and `supabase/migrations/0016_embedding_and_pgvector_foundation.sql`
(the single source of truth — this document explains it, it does not
replace reading the migration for exact behavior).

## The approved configuration

Exactly one `embedding_configurations` row may hold `approval_status =
'approved'` at a time (`embedding_configurations_one_approved_idx`, a
unique index on a constant expression filtered to approved rows). This
sprint seeds one: `noor-multilingual-e5-base-v1` — self-hosted
`intfloat/multilingual-e5-base`, MIT-licensed, revision pinned against
the live Hugging Face Hub API, 768 dimensions, L2-normalized output
compared by cosine distance. `external_processing = false` — no data
ever leaves Noor's own infrastructure. Normal users cannot create or
mutate configuration rows; there is no client-facing function for it.
Retiring a configuration never deletes existing vectors — it only
changes which configuration new work resolves against.

## Chunk-embedding identity

A chunk embedding is uniquely identified by the SHA-256 hash of:
organization ID, chunk ID, chunk checksum, chunking run ID, input-text
checksum, passage-input-template version, provider name/version, model
identifier/revision, embedding dimension, output normalization, distance
metric, and embedding-configuration version
(`app/embedding/identity.py::compute_chunk_embedding_identity_sha256`,
mirrored conceptually — not literally re-validated — by
`record_document_chunk_embedding`'s uniqueness enforcement). A changed
chunk checksum, model revision, input template, or dimension always
produces a new identity; the old vector is never silently reused for
semantically different content. At most one `succeeded` row may exist
per identity (`document_chunk_embeddings_one_succeeded_per_identity`).

## Query-embedding identity

A separate identity tuple: organization ID, evaluation dataset ID,
dataset checksum, query ID, query checksum, query-input-template
version, plus the same provider/model/dimension/normalization/metric/
configuration-version fields. Query embeddings are never generated from
client-supplied vectors, and a passage embedding is never reused as a
query embedding — `multilingual-e5-base` requires distinct `"query: "`/
`"passage: "` role prefixes, so the two embeddings for identical text
are mathematically different vectors by design.

## Input contract: exact accepted text, one required prefix

`passage_input = "passage: " + <exact accepted chunk text>`;
`query_input = "query: " + <exact authored query text>`. No guideline
title, page number, organization name, or synthetic heading is ever
prepended beyond this one required prefix — chunk text is never
mutated, translated, summarized, or cleaned. Every input's token count
is computed with the model's own tokenizer before any provider call; an
input exceeding `maximum_input_tokens` (512) fails closed with
`embedding_input_exceeds_model_limit` — it is never silently truncated,
and the chunk itself is never altered to make it fit.

## Vector validation

Every produced vector must have the exact expected dimension (768),
every component finite (no NaN, no ±Infinity), and a non-zero norm
before it is ever persisted (`app/embedding/provider.py::validate_raw_vector`,
enforced identically for the real provider and any fake used in tests).
The stored norm and checksum are informational metadata for
troubleshooting — never treated as a retrieval-confidence score.

## Vector checksum: `vector_serialization_v1`

Each component is converted to canonical IEEE-754 float32, packed
little-endian, concatenated in index order, and SHA-256'd
(`app/embedding/checksums.py::compute_vector_checksum`) — never derived
from `str()`/`repr()` of floats, which would be sensitive to
locale/precision-formatting differences a byte-level serialization is
not.

## Durable execution: one job per (chunking run, configuration)

One `document_embedding` job embeds every currently-eligible chunk from
one accepted chunking run under the one approved configuration
(`create_document_embedding_job`), with a per-chunk `running` →
`succeeded` progress row (`record_document_chunk_embedding`) enabling
safe partial-resume after a retry — a failed batch never discards
already-succeeded vectors, and the provider is never re-called for an
identity that already has a valid stored vector.
`finalize_document_embedding_run` requires every expected chunk to have
exactly one valid succeeded (or reused) embedding before marking the
run succeeded — no partial-success aggregate state is ever possible.

## Query embeddings: their own controlled path

Query embeddings for a frozen dataset are generated by a dedicated
`query_embedding_generation` job (`create_query_embeddings_for_dataset`)
— not folded into the vector-evaluation job. This mirrors chunk
embeddings' own "generate once, reuse many times" shape: the same
frozen dataset's query embeddings are reused across every vector
evaluation run at that configuration, never regenerated per run.

## Invalidation, never deletion

Operational embedding eligibility becomes false — without physically
deleting any vector — when the source chunk's review is reopened or
rejected, the chunking run is invalidated, or an upstream
extraction/OCR review is reopened/invalidated (the same
`get_document_embedding_readiness()` chain Sprint 1-D3 already
established). Existing vectors remain historically preserved for
reproducibility of past evaluation artifacts; production retrieval
built on an invalidated chunk is never available.

## What this sprint explicitly does not do

No hybrid retrieval, no reranking, no LLM calls, no query rewriting, no
clinician-facing vector search, no automated model selection, no
multiple simultaneous production embedding providers. The vector
baseline exists to be evaluated against S1-E1's frozen human judgments
and compared honestly with the lexical baseline — see
`vector-retrieval-and-evaluation.md`.
